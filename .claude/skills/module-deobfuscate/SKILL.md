# /module-deobfuscate — Поиск и деобфускация закрытых модулей

## Когда применять

Выгрузка конфигурации (`/db-dump-xml`) или обработки даёт закрытый модуль как
`Ext/Module.bin` (или `ObjectModule.bin`, `ManagerModule.bin`, `Form/Module.bin`)
**без** одноимённого `.bsl` рядом. Такой модуль нельзя ни прочитать, ни загрузить
обратно как текст — внутри контейнер с байткодом виртуальной машины 1С.

Скилл делает пять шагов: находит такие модули, вынимает байткод, декомпилирует
его в BSL без участия человека, раскладывает тексты обратно в выгрузку и
проверяет, что модули не оборваны.

## Использование

```
python <skill>/scripts/find_closed.py <каталог-выгрузки> [<отчёт.txt>]
python <skill>/scripts/extract_images.py <каталог-выгрузки> <каталог-image> <манифест.txt>
powershell -NoProfile -File <skill>/scripts/run_decompiler.ps1 -Manifest <манифест.txt> -Ref <имя-базы> [-Server localhost] [-Epf <epf>] [-WorkDir <каталог>] [-TimeoutSec 3600]
python <skill>/scripts/apply_bsl.py <каталог-выгрузки> <каталог-bsl>
python <skill>/scripts/check_bsl.py <каталог-bsl>
```

`<skill>` — каталог этого скилла. Пути можно относительные — скрипт сам сводит их
к абсолютным. `<каталог-выгрузки>` — корень выгрузки (`...\cf` для выгрузки
конфигурации). Перенаправление вывода (`| Out-File`) внутрь `powershell -File`
не работает — оборачивай в `powershell -Command "& { … } *>&1 | Out-File …"`,
иначе лишние токены уедут в параметры скрипта.

1. **Поиск.** `find_closed.py` печатает `размер путь` по каждому закрытому модулю
   и итоговое число. Код возврата 1 — закрытых модулей нет.
2. **Извлечение байткода.** `extract_images.py` пишет `<имя>.image` и манифест
   `<путь.image>|<путь.bsl>` (UTF-8 **без BOM**), отчёт — `extract_report.txt`
   рядом с манифестом. Имя image = путь `.bin` в выгрузке, `/` и `\` → `__`.
   Третье поле строки манифеста выбирает движок: без него — Ассемблер, `|addin` —
   внешняя компонента `AddIn.Deobfuscator1С` (см. «Бэкенд через компоненту»).
3. **Декомпиляция.** `run_decompiler.ps1` кладёт манифест в каталог обмена,
   копирует туда же `assets/WebExDeobfuscator1CWin64_1002.dll` (нужна для режима
   `addin`), запускает тонкий клиент с `assets/Assambler.epf` и ждёт `_report.log`.
   Логин/пароль берутся из `HKCU\Environment` (`V8_DB_USER`, `V8_DB_PASS`), если
   не переданы параметрами — в чат их не выводи. База подойдёт **любая
   управляемая** (`demo-base-2`, `demo-base`): конфигурация обработки самодостаточна.
   Строки отчёта: `OK|номер|длина-текста|путь-bsl`, `ERR|номер|путь-bsl|ошибка`.
   Копии `boot.log`, `addin.log` и `report.log` — в `<WorkDir>` (по умолчанию
   `.tmp/deobf-run`).
4. **Раскладка.** `apply_bsl.py` кладёт `.bsl` рядом с `.bin` и переименовывает
   `.bin` в `.bin.closed`, иначе у выгрузки два представления одного модуля.
   Отчёт — `apply_report.txt` рядом с `.bsl`. Повторный `find_closed.py` после
   раскладки должен оставить только упавшие модули.
5. **Проверка.** `check_bsl.py` сверяет число объявлений процедур/функций с
   числом концов и кодировку. Внимание: обрыв **тела** модуля, когда все
   `Конец*` на месте, счёт не ломает и такой обрыв не виден — см. «Дефекты
   текста и сверка». Затем `/db-load-xml` и `/db-update`, но учти: модуль из
   `.bsl` в базу ляжет **незащищённым** (защита была в `.bin`), а `.bin.closed` —
   посторонний файл для выгрузки, перед повторной выгрузкой в тот же каталог
   его надо убрать.

**Основной способ — наш декодер `bsl-deobfuscator`** (раздел ниже): шаги 1–3 заменяются
одним запуском `run.ps1`, клиент 1С, база и внешние компоненты не нужны; шаги 4–5 общие.
Ассемблер и `|addin` остаются для второго мнения и добора — см. «Протокол сомнений».

## Как это устроено

Формат `Ext/*.bin`: заголовок 16 байт, далее блоки `[дескриптор][нагрузка]`,
дескриптор — 29 байт ASCII `xxxxxxxx xxxxxxxx xxxxxxxx \r\n` (первое hex-поле —
размер нагрузки). Типовых блоков семь: индекс, таблица имён, **image**, два
служебных, заголовок `text` и последний блок — исходный текст модуля, но он
зашифрован/сжат и напрямую не читается.

`image` — блок, начинающийся с UTF-8 BOM и `{1,`; это текст байткода вида
`{"Cmd",<кол-во>,<точка-входа>,…}`, `{"Const",…}`, `{"Var",…}`, `{"Proc",…}`.
Его и декомпилирует Ассемблер.

`assets/Assambler.epf` = `Ассемблер.epf` из https://github.com/ProhorP/1C-inversion
+ `assets/batch-block.bsl` (пакетный блок) + зарегистрированное событие `OnOpen`.
Пересобрать после правки:

```
python <skill>/scripts/patch_editor_form.py <выгрузка-Ассемблера> <skill>/assets/batch-block.bsl [имя-формы]
# затем /epf-build по этой выгрузке
```

Что нужно знать, если правишь пакетный блок:

- Каталог обмена **зашит в модуль**: `C:\Users\Public\deobf\` (файлы `manifest.txt`,
  `boot.log`, `_report.log`). Меняешь — пересобирай EPF и меняй `-Handoff`.
- Файловый ввод-вывод — на **сервере** (`&НаСервере`), иначе тонкий клиент
  спрашивает разрешение на доступ к локальной файловой системе и headless-запуск
  висит на диалоге.
- `ПодключитьВнешнююКомпоненту()` и `УстановитьВнешнююКомпоненту()` на сервере
  **нет** — компоненту подключает клиент (см. следующий раздел), а `image` для
  движка Ассемблера читается с диска напрямую (`ПрочитатьМодульИзФайлаНаСервере`).
- Состояние модуля управляемой формы на сервере между вызовами **не
  сохраняется** — вызовы stateless, список модулей держит клиент.
- `ТекстМодуля.Очистить()` сразу после записи на диск: иначе мегабайтный текст
  уезжает на клиента и серверный вызов упирается в лимит размера.
- Управляемая форма модуля обработки не видит `ПараметрЗапуска()` и
  `ПолучитьПеременнуюСреды()` — параметры передаются только файлом.

## Бэкенд через компоненту (`|addin`)

`assets/WebExDeobfuscator1CWin64_1002.dll` — x64-компонента из макета
`Deobfuscator1_0_0_2` обработки «Деобфускатор байт кода 1С» (546 816 байт,
md5 `a6658a6e5e66502817e125aebdecc256`, экспорты `GetClassObject`,
`GetClassNames`, `DestroyObject`). Знакома с мусорными операторами обфускатора,
которыми движок Ассемблера спотыкается, и умеет сначала чистить байткод
(`Деобфусцировать`), потом декомпилировать (`Декомпилировать`). Строки манифеста
с третьим полем `|addin` идут через неё.

Что установлено замерами:

- Компоненту подключает **только клиент**: `ПодключитьВнешнююКомпоненту()` и
  `УстановитьВнешнююКомпоненту()` в контексте сервера платформой не определены
  (`/CheckConfig` отвечает «Процедура или функция с указанным именем не
  определена»). Подключение — `&НаКлиенте`, а весь файловый ввод-вывод
  остаётся `&НаСервере`, иначе тонкий клиент спросит про локальную ФС.
- Плагин — `Deobfuscator1СCurrent`, класс — `New("AddIn.Deobfuscator1СCurrent.Deobfuscator1С")`,
  тип `Native`, подключение `НеИзолированно`.
- Файл компоненты надо давать **локальным путём** (`C:\Users\Public\deobf\…dll`),
  адрес `ПоместитьВоВременноеХранилище()` клиент у сервера без веб-публикации не
  скачивает — `ПодключитьВнешнююКомпоненту()` молча возвращает `Ложь`.
- `СодержимоеФайла`/байткод компонента принимает **строкой** (ровно то, что даёт
  `ЧтениеТекста(Путь, UTF8).Прочитать()`), и строкой же возвращает текст модуля.
- `ИменаБлоков()` отдаёт JSON `{"names":[{"name":"…"},…]}`; чистку прогнать сначала
  по пустому имени блока, затем по каждому имени, с `ПринудительнаяНумерацияСтрок = Истина`.
- Свойство `ЗащитаОтОпасныхДействий` у `ЭтаФорма` в рантайме недоступно
  («Поле объекта не обнаружено»), читать его можно только через `Попытка`.
  Диалога подключения на практике не было: компонента из каталога обмена
  подключается без подтверждения.
- Ход подключения и длина ответа каждого модуля — в `addin.log` в каталоге обмена.

Замер (2026-11-04, те же два модуля, что не взял Ассемблер): `ОбменСEasyCeiling` —
684 023 символа BSL, `СофтФон` — 374 459, оба с **прямой** декомпиляцией, без
прогона чистки по блокам; весь сеанс — меньше минуты против ~1,5 мин на ошибку у
Ассемблера.

Замер (2026-11-21, два модуля «Потолки» 3.5.10, которые Ассемблер взял с
дефектами): `МобильныйКлиент` — 1 453 503, `РаботаССМС` — 305 305 символов,
весь прогон — меньше минуты, клиент после отчёта гасится. Второй способ — не
замена первому, а добор: он умеет то, чего Ассемблер не умеет, и одновременно
портит часть того, что у того получилось.

## Дефекты текста и сверка `|addin` с Ассемблером

Вывод замеров: результат `|addin` сверяй с результатом Ассемблера по тому же
байткоду, а не принимай на веру. Каталог первого прогона не удаляй — сверять
будет не с чем.

Что `|addin` делает систематически (косметика, к логике не относится):

- снимает **все** `Перем` (в `МобильныйКлиент` 1664 → 1) и комментарии после
  `КонецПроцедуры`/`КонецФункции`;
- удаляет му-му присваивания и му-му выражения обфускатора;
- нормализует регистр (`И`/`ИЛИ` → `и`/`или`), снимает лишние скобки, склеивает
  строки (`Если … Тогда Возврат …;` — в одну);
- схлопывает `Если` с пустой ветвью `Тогда`: код `Иначе` становится
  безусловным, семантика та же;
- ставит `Функция` там, где Ассемблер поставил `Процедура`, если в байткоде
  есть возврат значения (10 замен в `МобильныйКлиент`, в т. ч. вызов, стоящий
  в выражении, — это исправление, а не порча).

Где `|addin` теряет (проверять обязательно):

- **обрыв хвоста функции**: если тело `Если … Тогда` — единственный `Возврат`,
  а после `КонецЕсли` идёт второй `Возврат`, хвост выпадает целиком, включая
  `КонецЕсли`; в тексте `КонецФункции` стоит сразу после последнего
  содержательного оператора. `check_bsl.py` этого не видит — счёт сходится;
- **потерянная метка**: `Перейти ~<n>` без объявления `~<n>:` `|addin`
  воспроизводит 1:1 от Ассемблера (`РаботаССМС`, метка `~1`) и не
  восстанавливает.

Порядок сверки:

1. Нормализуй оба текста (trim, выкинуть пустые строки) и сравни списки
   заголовков `Процедура|Функция x<guid>(`: расхождение имён — потеря функции.
   Сравни также общее число содержательных строк (без `Перем`, му-му и
   комментариев).
2. Для функций, где тело `|addin` короче, отфильтруй `Перем`, му-му и
   комментарии, а остаток ищи в склеенном тексте `|addin` по скелету (без
   пробелов и скобок, нижний регистр). «Потерянные» строки `Возврат` часто
   ложные — `|addin` склеил их с `Тогда`.
3. Отдельно глазами: `Перейти ~` без метки, обрыв перед `КонецФункции`,
   `Если` с пустым телом.
4. Если Ассемблер по модулю дал `OK` — за базу берётся его текст, из `|addin`
   переносятся только типы объявлений (`proc2func`). Если Ассемблер дал
   `ERR` — модуль добирается `|addin`, но хвосты и метки ревизуются вручную.

## Третий движок — d0 BSL Decompiler (замер 2026-11-22)

`d0codesoft/bsl-1c-decompiler-public` v0.2.0 — сторонний x64-бинарь (PyInstaller,
внутри v8unpack 1.2.11, релиз собран 2026-11-20; SHA256SUMS проверить до запуска).
Интерфейс: `scan config.cf`, `decompile module-или-cf out [--object "Тип.Имя"]
[--ignore-errors]`, `restore текст.bsl -o out.bsl --no-deobfuscate --rename aggressive`.

Замер на тех же двух модулях «Потолки» 3.5.10, проверка сборкой платформы
`/epf-build -Checks modules -Context Server` (см. «Проверка платформой»):

| выход | МобильныйКлиент (130 методов) | РаботаССМС (67) |
|---|---|---|
| d0 `decompile` из контейнера модуля | 27 ошибок: 17 нет `КонецЕсли`, 6 нет `Исключение`, 3 нет `КонецФункции`, 1 нет `КонецЦикла` | 3 ошибки |
| d0 `decompile --ignore-errors` из CF | 92 ошибки `(None)`, потеряно 16 методов (114/130) | 22 ошибки, потеряно 9 методов (58/67) |
| d0 `restore` поверх текста `|addin` + правки `scripts/d0` | сборка OK | сборка OK |

Восстановление строк от множества `{"S",…}` image-блока: d0-`decompile` 814 (58,3 %) /
297, `|addin` и restore-путь 767 (54,9 %) / 297; совпадение строк с `|addin` у restore
93,4 % / 95,5 %. Нативный `decompile` богаче на константы, но теряет методы и ставит
`None` в аргументах вызовов — годным текстом сам по себе не становится.

### Маршрут починки `restore`

`<мод>.addin.bsl → flatten2 → fix_labels → restore --no-deobfuscate --rename aggressive → fix_goto → unflat`

- `flatten2.py` сплющивает продолжения и многострочные литералы в одну строку, режет
  `Тогда`/`Цикл` при теле на той же строке: без него парсер d0 падает
  (`incomplete IF header`, `raw newline inside string`);
- `fix_endif.py`, `fix_loops.py` закрывают `Если`/`Цикл`, срезанные на `Возврат`-ветках;
- `fix_try.py` выправляет порядок/пустоту `Исключение`/`КонецПопытки`;
- `fix_labels.py` вставляет метки под висящие `Перейти ~N`, `fix_goto.py` удаляет
  `Перейти` перед `Исключение` (метка сразу за `Исключение` недопустима);
- `unflat.py` возвращает `|` внутри строк в настоящие переводы строк.

Сами правки — косметика парсера, но счёт остатков смотри по сборке: она единственный
арбитр.

### Проверка платформой (без постоянной базы)

1. `cf_check` — копия XML-выгрузки рабочей конфигурации (`robocopy`), в ней
   `scripts/d0/stub_add.py <Имя>` добавляет пустой общий модуль-заглушку (шаблон
   `scripts/d0/stub_ОбщийМодуль.xml`) — иначе зов чужих модулей даёт
   «Переменная не определена»;
2. `/epf-init СинтаксКонтроль`, текст модуля — в `Ext/ObjectModule.bsl`;
3. `/epf-build -InfoBaseServer … -InfoBaseRef … -Checks modules -Context Server
   -ConfigSrc cf_check`. Ошибки печатаются строками `{Обработка…(стр,кол)}` —
   их и считай, файл не создаётся.

### `scan`/`decompile` по CF — что ломается

- Отчёт с телом-«справкой с картинками» (`{5,0,2,…}`) валит `decode_html_data` на всём
  CF. Лечение в выгрузке: всем отчётам без тела — пустой `Report.html`
  (`fix_report_body.py`) и html-форма `help` `["5","1","\"ru\"",["#base64:"],"0"]` в
  `Report.json` (`fix_report_help.py`, JSON — без BOM).
- `COMPILED_ONLY` d0 распознаёт по файлу `image` в сыром каталоге `<uuid>.N`. Штатный
  `v8unpack -E` блок `image` у закрытых модулей ТЕРЯЕТ, и упаковка `-B` его не
  возвращает — классификация молчит, `decompile` даёт `modules=0`. Обход: вынуть
  `image` из stage1 исходного CF и разложить как `<Класс>.<код>.image`, а в
  `v8unpack/MetaObject/__init__.py` дописать запись блока `image` в
  `write_encode_code` (и чтение в `encode_code`).

## Наш декодер — bsl-deobfuscator (тот же дамп, без клиента)

**Статус: основной способ деобфускации** (решение 27.11.2026). Основания: SkyLux
3.4.5.0 — 20/20 против 18/20 у Ассемблера (ERR на `ОбменСEasyCeiling`, `СофтФон`);
«Потолки» 3.6.15 — 21/21, `// ITER` 0, платформа и клиент чистые. Исходники
публиковать нельзя (лицензия d0-ядра) — поставка исполняемым файлом, сборка из
этого репозитория.

Собственный движок — `E:\Works\1C\LLM\bsl-deobfuscator` (локальная Gitea
`rumax/bsl-deobfuscator`): форк восстановленного ядра d0 с исправленными
дефектами (image-санитайзер, классы E6, структурный CFG-эмиттер `cfg_text.py`
вместо плоского `legacy_text.py`). Вход — тот же XML-дамп с `Ext/*.bin`, что у
шагов 1–2. Клиент 1С, база и внешние компоненты не нужны, поэтому движок годится
и для **живой серверной базы**: выгрузил → декомпилировал → загрузил навыком.

Конфиг на прогон (`config.example.json` в репозитории; пути абсолютные):

```json

  "dumpDir":    "E:/Works/1C/src/<база>/cf-<дата>",
  "basePath":   "",
  "runtimePy":  "E:/Works/1C/LLM/bsl-deobfuscator/runtime/py312/python.exe",
  "v8":         "C:/Program Files/1cv8/8.5.1.1529/bin",
  "skillsRoot": "E:/Works/1C/dev-playground/.qoder/skills"

```

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File `
  E:\Works\1C\LLM\bsl-deobfuscator\run.ps1 -Config D:\Temp\bsl-<проект>\config.json
```

Шаги внутри те же, что выше, но без клиента: `find_closed` → `extract_images` →
`sanitize_batch` (санитайзер обязан быть эквивалентным, иначе `ПРОВАЛ`) →
`cfg_text.py` по каждому image → `check_bsl`. Runner сам собирает
`BSL_COMMON_MODULES` из `CommonModules/*.xml` — это снимает `Перем`-головы с
именами общих модулей; `PYTHONHASHSEED=0` фиксирует порядок. Выход:
`<workDir>/run-<штамп>/bsl/<Модуль>.bsl`, ошибки по модулю — `logs/<Модуль>.err`,
соответствие image ↔ текст — `map.txt`.

Ключи: `-Build` — арбитр платформой (`epf-build -Checks modules -Context Server`),
`-Apply` — `apply_bsl.py` в выгрузку (`.bin` → `.bin.closed`), `-Load` —
`LoadConfigFromFiles -partial` + `UpdateDBCfg` для **файловой** базы (`/F`),
`-Verify` — контрольная выгрузка, md5, `find_closed`, DRIFT. `-Legacy` — откат на
плоский эмиттер (не применять: теряет циклы и инкременты).

**Серверная база** (`localhost/<база>`, как SkyLux): `-Load`/`-Verify` не годятся,
они про `/F`. После `-Apply` грузить навыком `db-load-xml -Mode Partial -UpdateDB`
со списком `run-<штамп>/load-files.txt` (пути относительно выгрузки, BOM+CRLF).

Замеры: «Потолки» 3.6.15 — 21 модуль, `// ITER` 0, загрузка RC=0 (см. E9);
SkyLux 3.4.5.0 от 27.11 — см. «Замер 27.11».

### Протокол сомнений

Любое сомнение — модуль не декомпилировался, текст выглядит неполным (обрыв перед
`КонецФункции`, висящий `Перейти ~` без метки, пустые ветки), конфигурация или клиент
падают, проверки расходятся — перепроверять модуль **тремя сторонними движками** по
тому же image:

1. **Ассемблер** — `run_decompiler.ps1` (шаг 3 «Использования»);
2. **`|addin`** — та же строка манифеста с третьим полем `|addin`;
3. **d0** — `decompile` / `restore` (раздел «Третий движок»).

Расхождение разобрать, **наш движок исправить**: правка в `src/bsl_decompiler`,
регрессионный тест в `tests/defects` (запуск из каталога: `python test_emitter_defects.py`),
повторный прогон и проверки. После исправления продолжаем использовать наш как основной;
сторонние движки — арбитры и добор, не замена.

### Исполняемая сборка

Исходники d0-ядра не публикуются; для поставки собирается `bsl-deob.exe`
(PyInstaller) скриптом репозитория:

```powershell
powershell -NoProfile -File tools/build_exe.ps1
# опционально: -Python <python.exe 3.12 с PyInstaller> -OutDir <куда положить exe>
```

Скрипт кладёт `dist-exe/bsl-deob.exe` и `BUILD.txt` (версия, md5, размер, время).
Режимы: `bsl-deob.exe <image> <out.bsl>` и `bsl-deob.exe --manifest <m.txt> [--out-dir <dir>]`
(строки `<image>|<bsl>`; `BSL_COMMON_MODULES` читается из окружения). В пакетном прогоне
exe подставляется флагом:

```powershell
powershell -File run.ps1 -Config <cfg.json> -Exe [-ExePath <bsl-deob.exe>]
```

Шаги `find_closed`/`extract_images`/`sanitize`/`check_bsl` остаются Python-скриптами
(окружение нужно и для `apply/load`), декомпиляция же идёт одним вызовом exe по
манифесту `san/*.image → bsl/*.bsl`; гейты и семантика OK/FAIL те же. Код требует
Python 3.12 (PEP 701 — вложенные кавычки в f-строках); окружение сборки — вне
системного диска (`uv python install 3.12`, `uv venv`, `uv pip install pyinstaller`).
Приёмка exe — сравнение md5 с Python-прогоном на контрольных модулях (27.11: два
модуля SkyLux совпали байт-в-байт) плюс те же гейты `check_bsl`/`/CheckConfig`.
Один exe — одна версия движка: после правок `src/` пересобрать и обновить `BUILD.txt`.

## Ограничения и скорость

- Декомпилятор — чистый код 1С, внешних компонент не требует. Работает на x64, в
  отличие от «Декомпилятора AWA», у которого `Cv8cf.dll` из макета `v8cf` —
  32-битный PE (machine `0x14C`) и на x64-платформах не загружается.
- Скорость ориентировочная: 8 КБ байткода — секунды, 300 КБ — десятки секунд,
  1,4 МБ — минуты. Полный прогон 20 модулей занял ~33 мин — ставь `-TimeoutSec`
  3600 и выше, а сам запуск выноси в detached-режим: длинный пакетный прогон не должен
  держать сеанс агента.
- Имена восстановлены не всегда: обфускатор успевает переименовать часть
  процедур, констант и переменных в `x<guid>`. В «Потолках» `Номенклатура` и
  `ПраваПользователей` остались с нормальными именами и `Экспорт`, а
  `РаботаСВебхук` и `ОбщийМодуль` — целиком `x<guid>`. Читаемость при этом
  сохраняется: строки, тексты запросов (в `ОбщийМодуль` — 86 вхождений `ВЫБРАТЬ`)
  и обращения к объектам типовой конфигурации не тронуты.
- Не каждый модуль поддаётся: движок Ассемблера не знает часть операторов,
  вставленных обфускатором, и тогда в отчёте
  `ERR|номер|путь-bsl|…Не предусмотрен оператор x<guid>…`. Замер на 20 закрытых
  модулях конфигурации «Потолки» 3.3.6.0 (прогон 2026-11-04, отчёт
  `.tmp/deobf-work/report_run1.log`): **18 OK / 2 ERR**, 10,2 МБ текста за
  ~33 мин (первый файл 01:05:08, последний 01:37:09), крупнейший модуль — 1,94 МБ
  BSL. Упали `ОбменСEasyCeiling` и `СофтФон` — их добрал режим `|addin`
  (итого **20 из 20**), см. предыдущий раздел.
- `find_closed.py` разделяет `Ext/*.bin` без `.bsl` на настоящие модули (есть
  image-блок) и прочее (макеты, картинки) — по одному только отсутствию `.bsl`
  судить нельзя: в выгрузке «Потолки» 91 кандидат, из них модулей 20.
- `run_decompiler.ps1` печатает «ОТДЕКОМПИЛИРОВАНО ВСЁ» и гасит клиент, даже
  если тот ещё работает: о завершении суди по `_report.log`, а не по строке
  вывода.
- Предупреждение `extract_images.py` «число скобок не совпадает» — не признак
  поломки: у `РаботаССМС` 3.5.10 оно есть, а оба движка дали по нему
  идентичный текст.
- Имена модулей с `__` внутри искажают обратное отображение в выгрузку — для
  `apply_bsl.py` раскладывай такие вручную.
- В выгрузке расширения (`cfe`) тот же формат; скилл работает по любому XML-дампу.
