# /bsp-postupgrade — очередь объектов после обновления

Навык про хвост обновления БСП 3.5.x: конфигурация складывает необработанные документы в регистр
сведений и показывает сервисную форму «Документы после обновления». Пока записи в очереди, обновление
считается незавершённым.

## Где лежит очередь

- **Рекомендуемые** — `РегистрСведений.ОбъектыКОбработкеПослеОбновленияРекомендуемые`; сюда пишет
  сервисная обработка и регламентное задание, её и обрабатывает `ОбработкаОбновлений.ОбработатьОбъект`.
  Большинство «зависших» записей — здесь.
- **Обязательные** — `...Обязательные`; пишутся при автоматическом обновлении версии, обрабатываются
  обработчиками самих версий (`Обработка_<версия>`-ветки общего модуля `ОбработкаОбновлений`).

Физически это таблицы `_InfoRg<N>`; состав полей — `_Fld<N+1>` (версия), `_Fld<N+2>_TYPE/_RTRef/_RRRef`
(ссылка), `_Fld<N+3>` (дата), `_Fld<N+4>` (текст результата). `_RTRef` — номер ОСНОВНОЙ таблицы типа
(`_Document138` = заказы, `_Document174` = реализации), таблиц `_Reference<RTRef>` может не быть —
ориентируйтесь на `_Document*`. Счёт и текст: `/db-sql-read -Command sql`.

## Как читать записи

Из 1С — `ВЫБРАТЬ ... ИЗ РегистрСведений.ОбъектыКОбработкеПослеОбновленияРекомендуемые` (у Обязательных
поля `ОбъектСсылка`/`ОбъектДата`, у Рекомендуемых `Документ`/`ДокументДата`). Составной тип ссылки —
сохраняйте именно ссылочное поле, а не имя из текста.

## Как обрабатывать

1. **Штатно**: регламентное задание `ОбработкаДокументовПослеОбновления` — но её процедура требует
   активности своего РЗ на текущий момент и валит всё, если расписание не покрывает «сейчас».
2. **Обходом из клиента**: `ОбработкаОбновлений.ОбработатьОбъект(Структура, Ложь)` по очередной записи
   (`ВерсияПрограммы`, `ВерсияПрограммыЧисло`, `Документ`/`ОбъектСсылка`, `ОбъектДата`/`ДокументДата`).
   **Из COM-коннекта модуль не инициализируется** — `Ошибка инициализации модуля ... Переменная не
   определена (УстановкаЦенСервер)`, потому что у зависимого модуля `УстановкаЦенСервер` снят флаг `ExternalConnection`. Гоняйте
   вызов через тонкий клиент: EPF с серверным циклом по регистру и задержкой ~3 с, `/Execute` и старт
   сеанса из стартового окна. Успешные объекты обработчик снимает сам, отказные остаются.
3. **Проверка до снятия вручную**: ветки-обработчики в основном только диагностируют. Для заказов
   (ВерсияПрограммыЧисло = 3005000999) — запрос остатков по продукции: минус = отказ, правится снятием
   дублей услуг в реализациях. Для реализаций — движения `РасчетыСПокупателямиПоТипамДокументов`
   должны существовать.

## Снятие записи без обработчика

Версии с порядком 999 (например 3005009999 у 3.5.9.0) в обработчиках не имеют своих ветвей —
запись не может быть обработана и снимается пустым набором с отбором:

```powershell
$mgr = $c.РегистрыСведений.ОбъектыКОбработкеПослеОбновленияРекомендуемые
$ns = $mgr.СоздатьНаборЗаписей()
$ns.Отбор.ВерсияПрограммы.Установить($вер)
$ns.Отбор.ВерсияПрограммыЧисло.Установить($число)
$ns.Отбор.Документ.Установить($ссылка)
$ns.Записать($true)
```

В PS-обвязке менеджер берут из коллекции `$c.РегистрыСведений` (свойство кириллицей может не
резолвиться — тогда через `InvokeMember`), поля `Отбор` — invoke-свойствами, у поля — `Установить(значение)`.


## Грабли очереди

- Регистр Обязательные пуст — не путайте его с Рекомендуемыми по имени таблицы: счёт через SQL должен
  сходиться с запросом 1С, иначе это другая таблица/тип.
- Ветка 21786 для заказов требует ровно `3005000999`; с другим числом (например 3.5.9.0/999) заказ в
  неё не попадает и обработка молча отдаёт «не успешно» — не считайте это ошибкой данных.
- Повторный запуск обработки без изменений в данных крутит те же отказы: сначала правьте причину
  (дубли, минусы, заполнение Продукции), потом гоняйте очередь.
- Даты MSSQL хранятся со сдвигом +2000 лет (`2019` лежит как `4019`, пустая — `2001-01-01`) — фильтры
  в SQL только через `DATEADD(year, 2000, …)`, см. `/db-sql-read`.
