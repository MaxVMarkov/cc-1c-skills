# /module-deobfuscate — Поиск и деобфускация закрытых модулей

## Когда применять

Выгрузка конфигурации (`/db-dump-xml`) или обработки даёт закрытый модуль как
`Ext/Module.bin` (или `ObjectModule.bin`, `ManagerModule.bin`, `Form/Module.bin`)
**без** одноимённого `.bsl` рядом. Такой модуль нельзя ни прочитать, ни загрузить
обратно как текст — внутри контейнер с байткодом виртуальной машины 1С.

Скилл делает пять шагов: находит такие модули, вынимает байткод, декомпилирует
его в BSL без участия человека, раскладывает тексты обратно в выгрузку и
проверяет, что модули не оборваны.

## Использование

```
python <skill>/scripts/find_closed.py <каталог-выгрузки> [<отчёт.txt>]
python <skill>/scripts/extract_images.py <каталог-выгрузки> <каталог-image> <манифест.txt>
powershell -NoProfile -File <skill>/scripts/run_decompiler.ps1 -Manifest <манифест.txt> -Ref <имя-базы> [-Server localhost] [-Epf <epf>] [-WorkDir <каталог>] [-TimeoutSec 3600]
python <skill>/scripts/apply_bsl.py <каталог-выгрузки> <каталог-bsl>
python <skill>/scripts/check_bsl.py <каталог-bsl>
```

`<skill>` — каталог этого скилла. Пути можно относительные — скрипт сам сводит их
к абсолютным. `<каталог-выгрузки>` — корень выгрузки (`...\cf` для выгрузки
конфигурации). Перенаправление вывода (`| Out-File`) внутрь `powershell -File`
не работает — оборачивай в `powershell -Command "& { … } *>&1 | Out-File …"`,
иначе лишние токены уедут в параметры скрипта.

1. **Поиск.** `find_closed.py` печатает `размер путь` по каждому закрытому модулю
   и итоговое число. Код возврата 1 — закрытых модулей нет.
2. **Извлечение байткода.** `extract_images.py` пишет `<имя>.image` и манифест
   `<путь.image>|<путь.bsl>` (UTF-8 **без BOM**), отчёт — `extract_report.txt`
   рядом с манифестом. Имя image = путь `.bin` в выгрузке, `/` и `\` → `__`.
   Третье поле строки манифеста выбирает движок: без него — Ассемблер, `|addin` —
   внешняя компонента `AddIn.Deobfuscator1С` (см. «Бэкенд через компоненту»).
3. **Декомпиляция.** `run_decompiler.ps1` кладёт манифест в каталог обмена,
   копирует туда же `assets/WebExDeobfuscator1CWin64_1002.dll` (нужна для режима
   `addin`), запускает тонкий клиент с `assets/Assambler.epf` и ждёт `_report.log`.
   Логин/пароль берутся из `HKCU\Environment` (`V8_DB_USER`, `V8_DB_PASS`), если
   не переданы параметрами — в чат их не выводи. База подойдёт **любая
   управляемая** (`demo-base-2`, `demo-base`): конфигурация обработки самодостаточна.
   Строки отчёта: `OK|номер|длина-текста|путь-bsl`, `ERR|номер|путь-bsl|ошибка`.
   Копии `boot.log`, `addin.log` и `report.log` — в `<WorkDir>` (по умолчанию
   `.tmp/deobf-run`).
4. **Раскладка.** `apply_bsl.py` кладёт `.bsl` рядом с `.bin` и переименовывает
   `.bin` в `.bin.closed`, иначе у выгрузки два представления одного модуля.
   Отчёт — `apply_report.txt` рядом с `.bsl`. Повторный `find_closed.py` после
   раскладки должен оставить только упавшие модули.
5. **Проверка.** `check_bsl.py` сверяет число объявлений процедур/функций с
   числом концов и кодировку — обрыв тела модуля виден сразу. Затем
   `/db-load-xml` и `/db-update`, но учти: модуль из `.bsl` в базу ляжет
   **незащищённым** (защита была в `.bin`), а `.bin.closed` — посторонний файл
   для выгрузки, перед повторной выгрузкой в тот же каталог его надо убрать.

## Как это устроено

Формат `Ext/*.bin`: заголовок 16 байт, далее блоки `[дескриптор][нагрузка]`,
дескриптор — 29 байт ASCII `xxxxxxxx xxxxxxxx xxxxxxxx \r\n` (первое hex-поле —
размер нагрузки). Типовых блоков семь: индекс, таблица имён, **image**, два
служебных, заголовок `text` и последний блок — исходный текст модуля, но он
зашифрован/сжат и напрямую не читается.

`image` — блок, начинающийся с UTF-8 BOM и `{1,`; это текст байткода вида
`{"Cmd",<кол-во>,<точка-входа>,…}`, `{"Const",…}`, `{"Var",…}`, `{"Proc",…}`.
Его и декомпилирует Ассемблер.

`assets/Assambler.epf` = `Ассемблер.epf` из https://github.com/ProhorP/1C-inversion
+ `assets/batch-block.bsl` (пакетный блок) + зарегистрированное событие `OnOpen`.
Пересобрать после правки:

```
python <skill>/scripts/patch_editor_form.py <выгрузка-Ассемблера> <skill>/assets/batch-block.bsl [имя-формы]
# затем /epf-build по этой выгрузке
```

Что нужно знать, если правишь пакетный блок:

- Каталог обмена **зашит в модуль**: `C:\Users\Public\deobf\` (файлы `manifest.txt`,
  `boot.log`, `_report.log`). Меняешь — пересобирай EPF и меняй `-Handoff`.
- Файловый ввод-вывод — на **сервере** (`&НаСервере`), иначе тонкий клиент
  спрашивает разрешение на доступ к локальной файловой системе и headless-запуск
  висит на диалоге.
- `ПодключитьВнешнююКомпоненту()` и `УстановитьВнешнююКомпоненту()` на сервере
  **нет** — компоненту подключает клиент (см. следующий раздел), а `image` для
  движка Ассемблера читается с диска напрямую (`ПрочитатьМодульИзФайлаНаСервере`).
- Состояние модуля управляемой формы на сервере между вызовами **не
  сохраняется** — вызовы stateless, список модулей держит клиент.
- `ТекстМодуля.Очистить()` сразу после записи на диск: иначе мегабайтный текст
  уезжает на клиента и серверный вызов упирается в лимит размера.
- Управляемая форма модуля обработки не видит `ПараметрЗапуска()` и
  `ПолучитьПеременнуюСреды()` — параметры передаются только файлом.

## Бэкенд через компоненту (`|addin`)

`assets/WebExDeobfuscator1CWin64_1002.dll` — x64-компонента из макета
`Deobfuscator1_0_0_2` обработки «Деобфускатор байт кода 1С» (546 816 байт,
md5 `a6658a6e5e66502817e125aebdecc256`, экспорты `GetClassObject`,
`GetClassNames`, `DestroyObject`). Знакома с мусорными операторами обфускатора,
которыми движок Ассемблера спотыкается, и умеет сначала чистить байткод
(`Деобфусцировать`), потом декомпилировать (`Декомпилировать`). Строки манифеста
с третьим полем `|addin` идут через неё.

Что установлено замерами:

- Компоненту подключает **только клиент**: `ПодключитьВнешнююКомпоненту()` и
  `УстановитьВнешнююКомпоненту()` в контексте сервера платформой не определены
  (`/CheckConfig` отвечает «Процедура или функция с указанным именем не
  определена»). Подключение — `&НаКлиенте`, а весь файловый ввод-вывод
  остаётся `&НаСервере`, иначе тонкий клиент спросит про локальную ФС.
- Плагин — `Deobfuscator1СCurrent`, класс — `New("AddIn.Deobfuscator1СCurrent.Deobfuscator1С")`,
  тип `Native`, подключение `НеИзолированно`.
- Файл компоненты надо давать **локальным путём** (`C:\Users\Public\deobf\…dll`),
  адрес `ПоместитьВоВременноеХранилище()` клиент у сервера без веб-публикации не
  скачивает — `ПодключитьВнешнююКомпоненту()` молча возвращает `Ложь`.
- `СодержимоеФайла`/байткод компонента принимает **строкой** (ровно то, что даёт
  `ЧтениеТекста(Путь, UTF8).Прочитать()`), и строкой же возвращает текст модуля.
- `ИменаБлоков()` отдаёт JSON `{"names":[{"name":"…"},…]}`; чистку прогнать сначала
  по пустому имени блока, затем по каждому имени, с `ПринудительнаяНумерацияСтрок = Истина`.
- Свойство `ЗащитаОтОпасныхДействий` у `ЭтаФорма` в рантайме недоступно
  («Поле объекта не обнаружено»), читать его можно только через `Попытка`.
  Диалога подключения на практике не было: компонента из каталога обмена
  подключается без подтверждения.
- Ход подключения и длина ответа каждого модуля — в `addin.log` в каталоге обмена.

Замер (2026-11-04, те же два модуля, что не взял Ассемблер): `ОбменСEasyCeiling` —
684 023 символа BSL, `СофтФон` — 374 459, оба с **прямой** декомпиляцией, без
прогона чистки по блокам; весь сеанс — меньше минуты против ~1,5 мин на ошибку у
Ассемблера.

## Ограничения и скорость

- Декомпилятор — чистый код 1С, внешних компонент не требует. Работает на x64, в
  отличие от «Декомпилятора AWA», у которого `Cv8cf.dll` из макета `v8cf` —
  32-битный PE (machine `0x14C`) и на x64-платформах не загружается.
- Скорость ориентировочная: 8 КБ байткода — секунды, 300 КБ — десятки секунд,
  1,4 МБ — минуты. Полный прогон 20 модулей занял ~33 мин — ставь `-TimeoutSec`
  3600 и выше, а сам запуск выноси в detached-режим: длинный пакетный прогон не должен
  держать сеанс агента.
- Имена восстановлены не всегда: обфускатор успевает переименовать часть
  процедур, констант и переменных в `x<guid>`. В «Потолках» `Номенклатура` и
  `ПраваПользователей` остались с нормальными именами и `Экспорт`, а
  `РаботаСВебхук` и `ОбщийМодуль` — целиком `x<guid>`. Читаемость при этом
  сохраняется: строки, тексты запросов (в `ОбщийМодуль` — 86 вхождений `ВЫБРАТЬ`)
  и обращения к объектам типовой конфигурации не тронуты.
- Не каждый модуль поддаётся: движок Ассемблера не знает часть операторов,
  вставленных обфускатором, и тогда в отчёте
  `ERR|номер|путь-bsl|…Не предусмотрен оператор x<guid>…`. Замер на 20 закрытых
  модулях конфигурации «Потолки» 3.3.6.0 (прогон 2026-11-04, отчёт
  `.tmp/deobf-work/report_run1.log`): **18 OK / 2 ERR**, 10,2 МБ текста за
  ~33 мин (первый файл 01:05:08, последний 01:37:09), крупнейший модуль — 1,94 МБ
  BSL. Упали `ОбменСEasyCeiling` и `СофтФон` — их добрал режим `|addin`
  (итого **20 из 20**), см. предыдущий раздел.
- `find_closed.py` разделяет `Ext/*.bin` без `.bsl` на настоящие модули (есть
  image-блок) и прочее (макеты, картинки) — по одному только отсутствию `.bsl`
  судить нельзя: в выгрузке «Потолки» 91 кандидат, из них модулей 20.
- Имена модулей с `__` внутри искажают обратное отображение в выгрузку — для
  `apply_bsl.py` раскладывай такие вручную.
- В выгрузке расширения (`cfe`) тот же формат; скилл работает по любому XML-дампу.
