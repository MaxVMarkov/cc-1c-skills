# Справочник по платформе (1c-syntax-helper MCP)

Навыки оперируют **структурой**: XML-форматами, DSL и CLI конфигуратора. Им неотличимо, какой
синтаксис у глобальной функции и что умеет метод платформенного типа — код модулей агент пишет «по
памяти модели». Для этого снаружи стоит MCP-сервер [`1c-syntax-helper`](https://github.com/MaxVMarkov/1c-syntax-helper-mcp):
поиск по документации платформы (`find_1c_help`, `get_syntax_info`, `get_quick_reference`,
`search_by_context`, `list_object_members`).

> **Скилы работают без справочника.** Он опционален: комплект лишь объявляет, где его искать, и
> даёт пробу доступности. Но там, где справочника нет, ошибка выглядит иначе, чем ошибка.

## Зачем проверять наличие

Ответ поискового инструмента пуст по двум неразличимым причинам: «такого нет» и «справочник не
проиндексирован / сервер не поднят». Отсюда правило для навыков, генерирующих код модулей:

- перед тем как отрицать существование метода по пустому ответу — проверить, готов ли справочник;
- если справочника нет — отрицать нельзя, и проверкой синтаксиса служит конфигуратор
  (`/db-load-xml` + валидация), а не молчаливое доверие модели.

Скрипт навыка MCP вызвать не может — это инструмент агента. Проверить же, поднят ли сервер, скрипт
может по HTTP напрямую:

```bash
powershell.exe -NoProfile -File scripts/ref-mcp.ps1          # + -Tools, чтобы увидеть состав инструментов
```

| Код | Смысл | Что делать |
|:---:|-------|-----------|
| 0 | сервер здоров, индекс построен | вопросам про синтаксис верим |
| 1 | отвечает, но нездоров или индекс пуст | ответам поиска не верим |
| 2 | недоступен | справочника нет — синтаксис проверяем конфигуратором |

## Что где искать

| Вопрос | Источник |
|--------|----------|
| как устроен файл (XML, DSL, свойства объекта) | `docs/1c-*-spec.md`, `docs/*-dsl-spec.md` |
| как писать код модуля (функции, методы, типы платформы) | справочник MCP |
| что лежит в конкретной конфигурации / информационной базе | `/meta-info`, `/cf-info`, XML-выгрузка — **не** MCP |

Последняя строка — главный источник ошибок. Справочник знает **платформу**, а не ваше
прикладное решение: объекта `Справочник.Номенклатура` в нём нет и быть не может, есть шаблон
`Справочник.<Имя справочника>`.

## Границы (замеры 2026-10-04, платформа 8.5.1)

| Запрос | Результат |
|--------|-----------|
| `find_1c_help("ОткрытьФорму")` | ✅ глобальные функции, с английским алиасом и описанием |
| `search_by_context(query, context:"object", object_name:"Запрос")` | ✅ метод + одноимённые на других объектах |
| `list_object_members("Запрос")` | ✅ полный состав платформенного типа |
| `find_1c_help("Справочник")` | ✅ только **шаблоны** (`Справочник.<Имя справочника>`, коллекция `Справочники`) |
| `list_object_members("Справочник.Номенклатура")` | ❌ «не найден» — справочник про платформу |
| `find_1c_help("ПакетноеОбновлениеТаблицы")` | ❌ пусто — имена свойств/методов ищутся плохо |

Правила, которые из этого следуют:

- `search_by_context` требует параметр `context` (`global` / `object` / `all`); без него вызов отклоняется;
- объекты платформы индексированы под именами документации: вместо `ОписаниеМетаданных` —
  `ОбъектМетаданныхКонфигурация`;
- пустой ответ поиска — не доказательство. Проверьте положительным контролем по тому же объекту
  (`list_object_members`) или пробой доступности выше.

## Подключение

### Плагином (рекомендуется)

В комплекте лежит [`.mcp.json`](../.mcp.json) — сервер объявляется вместе с навыками, отдельной
настройки не нужно. Claude Code подхватывает корневой `.mcp.json` при `/plugin install`. Имя сервера
в списке инструментов — `plugin:<имя плагина>:<1c-syntax-helper>`, tools —
`mcp__plugin_1c-skills_1c-syntax-helper__find_1c_help` (дефисы в именах сохраняются).

**Qoder: только установка архивом (проверено 2026-10-04).** Плагин ставится через панель плагинов →
*Upload Plugin* → ZIP. Требование к архиву жёсткое: манифест лежит **в корне** архива
(`.qoder-plugin/plugin.json`, затем `.claude-plugin/plugin.json`) — обработчик ищет его там и бросает
`EXTENSION_PLUGIN_LAYOUT_UNSUPPORTED`, если в корне нет ни манифеста, ни маркеров раскладки
(`skills/`, `commands/`, `agents/`, `hooks/hooks.json`, `.mcp.json`). Папку-обёртку сверху класть нельзя.
Минимальный набор: `.qoder-plugin/`, `.claude-plugin/`, `.mcp.json`, `.claude/skills/`, `hooks/`,
`scripts/`; `tests/` и `.git` не нужны (при копировании установки `.git`, `node_modules`, `.env*`
отсекаются). Пример:

```powershell
Compress-Archive -Path .qoder-plugin, .claude-plugin, .mcp.json, .claude, hooks, scripts, docs, README.md, LICENSE -DestinationPath 1c-skills-0.1.0.zip
```

После установки появляются строка `1c-skills@local` в `~/.qoder/plugins/installed_plugins_v2.json`,
каталог `~/.qoder/plugins/cache/local/1c-skills/<version>/` и флаг в `enabledPlugins`; сервер
поднимается в следующей сессии (`[MCP] Server 'plugin:1c-skills:1c-syntax-helper' connected`).
Копия снапшотная: правки репозитория доходят только через перевыпуск архива и повторную установку.

Не работает маршрут «объявить маркетплейс и включить флаг»: `extraKnownMarketplaces` +
`enabledPlugins` в `~/.qoder/settings.json` загружают навыки и хуки, но плагин не становится
установленным — в панели он не виден (исключается из списка доступных как уже «занятый»), а его
MCP-сервер не стартует. Ошибки при этом нет никакой.


### Вручную

В MCP-настройки редактора/агента:

```json
{
  "mcpServers": {
    "1c-syntax-helper": { "type": "http", "url": "http://localhost:8000/mcp" }
  }
}
```

### Предпосылки на машине

Объявление сервера ≠ его запуск. Справочник поднимается из своего репозитория и весит больше, чем
плагин:

1. Docker; внутри — Elasticsearch и сам MCP-сервер (`docker compose up -d`, порт 8000);
2. **файлы документации `.hbk` в `data/hbk`** — они не лежат в git, каждый кладёт свои;
3. сборка индекса после добавления файлов (см. `REINDEX_GUIDE.md` того репозитория).

Без пунктов 2–3 сервер жив, но пуст — это код возврата `1` пробы, и он опаснее выключенного
справочника: ответы «не найдено» приходят исправно.

### Другой адрес (общий сервер)

URL в `.mcp.json` жёсткий — так комплект работает из коробки. Подстановка вида
`${user_config.<ключ>}` платформой поддерживается (значения — из `pluginConfigs` в настройках), но
**без значения ключа строка уходит как есть**, то есть встроенного фолбэка нет. Для удалённого
сервера правьте `url` в `.mcp.json` копии плагина или заведите запись в собственных настройках MCP.

## Как называть инструменты в текстах навыков

Префикс зависит от платформы и от способа подключения: `mcp__1c_syntax_helper__find_1c_help` при
ручной настройке, `mcp__plugin_1c-skills_1c-syntax-helper__find_1c_help` при установке плагином
(дефисы в именах плагина и сервера сохраняются — проверено на установленных плагинах Qoder). В
инструкциях, описаниях и комментариях — только голые имена (`find_1c_help`, `list_object_members`).

## План на будущее — путь к скриптам в plugin-версии

В SKILL.md скрипты вызываются как `${CLAUDE_SKILL_DIR}/scripts/<имя>.ps1`. Плейсхолдер раскрывается
только там, где его раскрывает сама платформа:

- **Claude Code** — раскрывает сам; именно поэтому `switch.py` для цели `claude-code` оставляет
  плейсхолдер нетронутым, а для всех остальных платформ разворачивает путь.
- **Qoder** — в тексте навыка раскрывает `${QODER_SKILL_DIR}`, `${QODER_SESSION_ID}`,
  `${QODER_CONFIG_DIR}`, `${QODER_USER_CONFIG_DIR}`, а для навыка, пришедшего из плагина, ещё
  `${QODER|CLAUDE}_PLUGIN_ROOT` и `${QODER|CLAUDE}_PLUGIN_DATA`. `${CLAUDE_SKILL_DIR}` в рантайме не
  встречается вовсе (0 вхождений в `qoder-worker-runtime`), то есть уходит модели литералом.
  `${QODER_PROJECT_DIR}` раскрывается только в MCP-конфиге, не в тексте навыка. Проверено по коду
  рантайма, не по живой ошибке вызова.

Поэтому текущее решение — **только под Qoder, два канала вместе**: плагин из архива даёт навыки, хуки и
MCP-справочник, а `switch.py qoder` даёт развёрнутые относительные пути в скриптах
(`.qoder/skills/<навык>/scripts/…`). Второй канал обязателен, пока в исходниках остался плейсхолдер:
plugin-версия навыков со скриптами пути не разрешает.

Возможный шаг в будущем — заменить `${CLAUDE_SKILL_DIR}` на путь от корня плагина
(`${CLAUDE_PLUGIN_ROOT}/.claude/skills/<навык>/scripts/…`) во всех SKILL.md и сделать плагин единственным
каналом доставки. Цена: такие вызовы перестают работать вне плагина (проектная копия, `Download ZIP`,
другие платформы), то есть нужен либо отдельный прогон `switch.py`, переписывающий префикс под каждый
канал, либо двойная запись вызовов. Оба варианта не выбраны; ветки `port-qoder*` и сейчас собираются
автоматически, так что польза замены — только убрать локальную копию из схемы Qoder.
